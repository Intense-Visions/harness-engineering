# ADR-001: The requirements-authoring / spec-authoring boundary

- **Status:** Accepted
- **Date:** 2026-07-09
- **Context:** Roadmap #709 — Product Requirements skill (close the PRD middle)
- **Spec:** `docs/changes/product-requirements-skill/proposal.md`

## Context

The lifecycle had a gap between `product-advisor` (which authors a Business Requirements
Document) and `harness-brainstorming` (which authors a spec/proposal). Product-level
requirements — user stories, acceptance criteria, prioritization — were fused into the
proposal, so they were never authored deliberately and `acceptance-eval` had weaker material
to judge. Closing this "PRD middle" required deciding **where the PRD lives** and **how
forcefully it enters the pipeline**. Two decisions set a durable lifecycle boundary that
future lifecycle skills (UAT/sign-off, dashboard lanes) will build on, so they are recorded
here.

## Decision D1 — The PRD is a standalone, durable artifact

The `product-requirements` skill writes a durable PRD to
`docs/product-requirements/<item>/prd.md`, mirroring how `product-advisor` writes
`docs/inception/<engagement>/brd.md`. The alternative — embedding requirements directly into
the spec's `## Success Criteria`, or folding a "requirements" phase into
`harness-brainstorming` — was rejected because:

- It keeps the **non-technical authoring edge first-class**. A standalone, code-free artifact
  is a role-shaped front door (per `STRATEGY.md` — Full-lifecycle reach); burying requirements
  inside an engineer-facing skill works against that bet.
- It preserves a clean **skill boundary**: `product-advisor` authors the BRD →
  `product-requirements` authors the PRD → `harness-brainstorming` authors the spec →
  `acceptance-eval` judges the spec's criteria. Each skill owns exactly one artifact.

The drift risk of two documents (PRD + spec) is bounded by a tight handoff: the PRD's EARS
acceptance criteria **seed** the spec's `## Success Criteria` (they are not maintained in two
places — the spec is the judged source of truth, the PRD is its authored origin).

## Decision D3 — The PRD step is optional-but-wired, not a mandatory gate

`harness-brainstorming` consumes the PRD **when present** and runs unchanged when absent;
`harness-roadmap-pilot` suggests the PRD step for feature-shaped items. A mandatory
pre-spec gate was rejected because most roadmap items (bugs, chores, enforcement, refactors)
gain nothing from user stories — forcing a PRD there is the speculative ceremony YAGNI
forbids. Optional-but-wired keeps the PRD a first-class, discoverable step for feature work
without imposing it universally.

## Consequences

- **Positive:** clean per-skill artifact ownership; a non-technical front door; measurable
  criteria authored upstream of the spec, improving `acceptance-eval` material; no ceremony on
  non-feature items.
- **Negative / accepted:** a `harness-brainstorming` branch ("PRD present?") is now part of its
  contract; PRD↔spec require the seeding handoff to stay coherent (mitigated by making the spec
  the single judged source of truth).
- **Follow-ons (not in scope here):** a shared guided-interviewer extraction across
  `product-advisor` / `product-requirements` / `strategy` / `pulse`; a mechanical `prd_lint`
  enforcing the completeness rubric as constraints-as-code; role-shaped dashboard lanes
  (roadmap #711).
