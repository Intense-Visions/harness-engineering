# bug-fleet — proactive undiscovered-bug hunt across the standing codebase

**Status:** Draft · **Tier:** Large · **Type:** rigid skill (orchestrator)
**Family:** `-fleet` (a quality-queue member working alongside the core conveyor)
**Keywords:** fleet, orchestration, batch, bug-hunt, latent-defect, reproduction, failing-test, adversarial-review, risk-ranking, fan-out, worktree, batch-review

## Overview

Every existing correctness gate in the harness looks at code that is already suspect. `cicd-fleet` works failures that have **already manifested** as red or flaky CI. `harness-debugging` is **reactive** — it starts from a known problem. `harness-code-review`, `harness-security-review`, and `harness-soundness-review` are **diff- or spec-scoped** — they review what changed, not what is standing. `test-fleet` chases coverage, where bugs are only an incidental by-product (it already parks suspected bugs and hands them back for a human to route — evidence: `agents/skills/claude-code/test-fleet/SKILL.md:170`). The `-craft` family judges taste, not correctness. Nothing in the toolset proactively sweeps **already-merged, standing code** for defects nobody has hit yet.

`bug-fleet` fills that gap. It ranks the codebase into risk-ordered **areas**, confirms the batch with the human once, fans out worktree-isolated subagents that each run the **real** per-area hunt pipeline over standing code, and returns a tiered batch: **fix PRs** for verified bugs with a safe, bounded fix, and **filed issues** for verified bugs whose fix is risky or large. It is a **quality-queue** member of the `-fleet` family — it does not sit on the core intake → decide → build → land spine but works the latent-defect queue alongside it (as `cicd-fleet` works CI-red runs, `test-fleet` coverage gaps, and `cleanup-fleet` entropy hotspots).

The defining property is its verification bar. Bug-hunting LLMs hallucinate defects at a high rate, so a proactive hunter with a weak bar is not a signal generator — it is a backlog spammer that costs more attention than it saves. `bug-fleet` therefore adopts an **Iron Law of REPRODUCTION-REQUIRED**: a candidate defect is not a bug until a failing test reproduces it, deterministically, against unmodified code. No repro → discarded, never filed. Everything else in the design serves that bar.

### Goals

- Turn a risk-ranked sweep of the standing codebase into a batch of **verified** bugs, each carrying a reproducing failing test, with a single up-front human touchpoint plus one batch review.
- Hold an uncompromising reproduction bar so the fleet's output is trustworthy signal, not backlog noise.
- Dogfood the real per-area pipeline (the review machinery for the hunt, `harness-tdd` for the reproducing test, `harness-debugging` for the fix) — never hand-implement or short-cut it, and prove it ran by the session artifacts it leaves behind.
- Make adherence auditable on two independent axes: **pipeline provenance** (the real skills ran) and **repro evidence** (the bug is real — the test fails on unmodified code and passes only after the fix), plus all-OS CI green on any fix PR.
- Compose the existing detection and review skills for the queue and the hunt — reimplement neither.
- Never auto-merge; the human lands the batch (optionally via `pr-fleet`).

### Non-goals (YAGNI)

- Auto-merging fix PRs.
- Filing anything that lacks a deterministic reproducing failing test — including high-confidence, "obviously real" reviewer findings.
- Reimplementing hotspot detection, impact analysis, or the review reasoning — the queue and the hunt are built by composing existing skills.
- Fixing risky or large defects autonomously — those are filed with their reproducing test attached.
- Security-specific machinery and supply-chain risk — `bug-fleet` owns **general correctness**. A candidate that is a security vulnerability is **security-routed**: reported to the human with its reproducing test held on the pushed branch, never patched inline and never published as an exploit on a public issue. Disclosure is the human's call.
- Diff-scoped review of in-flight changes — that is `harness-code-review`.
- Coverage-driven test authoring — that is `test-fleet`; `bug-fleet` writes tests only as reproduction evidence.
- Building a physical shared `-fleet` library — the shared contract is documented in `docs/reference/fleet-family.md`, not extracted into code.

## Decisions made

1. **Build on the documented family spine; define only the stage-specific parts.** `bug-fleet` reuses the shared five-phase skeleton (SELECT → CONFIRM → DISPATCH → VERIFY → terminal), the concurrency governor, the artifact + all-OS-CI verification discipline, the worktree fan-out with its `.claude/`-nested push caveat, the one-up-front-CONFIRM/park-unforeseen interaction model, and the never-silent-merge invariant — all stated once in `docs/reference/fleet-family.md` (evidence: `docs/reference/fleet-family.md`). The `SKILL.md` cites that page rather than restating it, and defines only what is `bug-fleet`'s own: its queue, its hunt taxonomy, its reproduction-gated verification, its tiered terminal act, and its domain-specific rationalizations.

2. **Queue: disjoint codebase areas ranked by latent-defect risk, built by composing existing analyses.** SELECT enumerates **areas** (one coherent module or subsystem = one hunt = one worktree) by folding together `harness-hotspot-detector` (co-change + churn → structural risk), `get_critical_paths` (execution paths whose failure has the widest consequence), `harness-impact-analysis` / `compute_blast_radius` (dependents and blast radius), a git-churn pass, and `harness-test-advisor`'s coverage depth used **only as a risk multiplier** (thin coverage over high-risk code is where latent defects survive). Suspected bugs previously **parked by `test-fleet`** seed the queue as pre-scored candidate areas. Areas are required to be **disjoint** — a file belongs to exactly one area — so two worktrees never hunt the same code and produce duplicate candidates. Rationale: all of these analyses already exist and are battle-tested (evidence: `agents/skills/claude-code/harness-hotspot-detector/`, `agents/skills/claude-code/harness-impact-analysis/`, `agents/skills/claude-code/harness-test-advisor/`); a fleet's value is orchestration and batch review, not a second analysis engine. Missing any one source degrades to the others rather than aborting. Coverage is a **ranking input only** — closing coverage gaps is `test-fleet`'s job.

3. **Hunt: compose the existing review machinery over standing code, with the adaptations standing-code scope requires.** The per-area hunt runs the real review reasoning — the **adversarial** reviewer constructing failure scenarios, plus the **security**, **typescript-strict**, and **frontend-races** reviewers — over the area's **existing** code (evidence: `agents/skills/claude-code/harness-code-review/SKILL.md:293-296` defines the activation set; `:441-466` defines the three specialized reviewers; `agents/personas/adversarial-reviewer.yaml`). Because that machinery is diff-shaped, four adaptations are stated explicitly rather than assumed:
   - **Whole-area scope.** The area's standing code is presented as a whole-area scope (mechanically, a diff of the area against the empty tree), so every line is in scope rather than only recently-changed lines. Deep tier is therefore expected, not exceptional.
   - **MECHANICAL is informational, never a stop.** `harness-code-review`'s mechanical phase halts the pipeline on a red suite or failing `tsc` (evidence: `agents/skills/claude-code/harness-code-review/SKILL.md`). For a standing-code hunt that would make any repo with one pre-existing red test un-huntable — and a pre-existing failure is itself a lead. The hunt **records** the mechanical result and proceeds.
   - **Area size is bounded** (default 40 files / 4,000 LOC; larger modules split into sub-areas) so the whole-area fan-out stays inside the reviewers' context ratio instead of degrading to "prioritize ruthlessly".
   - **`harness-security-review` runs in full mode**, not the changed-files mode a diff would select, so its threat-model phase actually runs.

   The reviewers' own activation set is honored: the `frontend-races` reviewer activates only for async-UI areas, so a non-UI area runs three reviewers, not four. Rationale: the reviewers already encode the failure-scenario, invariant, and edge-case reasoning this member needs; reimplementing it would fork the reasoning and drift.

4. **Iron Law — REPRODUCTION-REQUIRED, with an adversarial refutation pass in front of it.** Each candidate defect passes two gates before it can be called a bug. First **REFUTE**: an adversarial pass that actively tries to prove the candidate _cannot_ occur (guarded upstream, unreachable, prevented by the type system, already covered by an existing test). Second **REPRODUCE**: a failing test authored via the real `harness-tdd` skill that observably **fails against unmodified code**, **deterministically** — run three times at the pinned base with a consistent red result; a flaky repro is discarded, because a test that fails by chance satisfies red-on-base by chance. A candidate that survives refutation but cannot be reproduced within the confirmed attempt budget (default 2) is **discarded, never filed**. REFUTE is retained for one measurable reason — it removes the plausible-but-impossible class before the expensive reproduction attempt, saving the batch's budget — and it is kept honest by recording every refuted candidate, with its refutation reason, in the batch summary so a human can spot-check what was dropped. Rationale: bug-hunting LLMs hallucinate defects at a high rate, and an executable, deterministic repro is the only evidence that cannot be hallucinated. This bar is the difference between a signal generator and a backlog spammer — the single most important property of this member.

5. **Terminal act: TIERED — fix PR or filed issue, decided by fix risk, never by bug severity.** A verified bug whose fix is **bounded-safe** (confined to the area, no public-API or observable-contract change, no cross-module refactor, no schema/migration change) is fixed via the real `harness-debugging` pipeline and emitted as a **fix PR carrying the now-passing reproducing test** — **one PR per verified bug**, so each is independently reviewable and independently revertible (the same granularity rationale `cleanup-fleet` applies to its targets). A verified bug whose fix is **risky or large** is emitted as a **filed issue**: its reproducing test is pushed as a test-only `repro/<slug>` branch and the issue links that branch and quotes the test source, so both VERIFY and the eventual fixer can run it. Rationale: a bug proven by a failing test is far safer to auto-fix than a subjective quality rewrite, so `bug-fleet` leans toward fixing more than `cleanup-fleet` does with its risky class — but the reproducing test proves the _defect_, not the _fix_, so a fix whose blast radius a bulk review could not hold in its head stays a human decision. Tiering on fix risk (not on how bad the bug is) keeps the boundary mechanical.

6. **Verification: two independent artifacts — pipeline provenance and repro evidence — plus all-OS CI green, never a self-report.** The family invariant requires an artifact proving the **real per-item pipeline ran**; the Iron Law additionally requires proof the **bug is real**. One artifact cannot do both jobs — a hand-written test and a hand-applied patch would satisfy a repro check while proving no pipeline ran — so VERIFY checks both:
   - **Provenance:** the `harness-tdd` (and, for fix items, `harness-debugging`) session state the per-area pipeline necessarily leaves behind under `.harness/sessions/<slug>/`. Absent provenance = the pipeline did not run = rejected, exactly as a missing plan directory rejects a `roadmap-fleet` item.
   - **Repro evidence, transplanted and re-run:** VERIFY checks out the **pinned batch base SHA** into a scratch worktree, applies **only the test file(s)** from the item's branch, and runs them. The result must be an **assertion failure** — a compile, import, or module-resolution error means the test depends on the fix rather than reproducing the defect, and the item is **rejected**, not verified. It then runs the same test on the branch (must pass), confirms the rest of the suite stayed green, and confirms CI is green on all three operating systems plus the enforce and harness checks. File-only items are verified the same way against their `repro/<slug>` branch: red at the pinned base, no fix present.

   Rationale: red-on-base/green-on-branch is a mechanically checkable two-sided proof, and pinning one batch-wide base SHA at CONFIRM keeps it from being a moving target across a multi-hour batch. A rejected item is **retried once**; still failing, it is reported as rejected and the batch continues.

7. **Boundary with security.** The security reviewer participates in the hunt as a **correctness lens**, but a candidate that is genuinely a security vulnerability is **security-routed**: it terminates as its own verdict, is reported to the human with the reproducing test held on the pushed branch, and is **never patched inline and never published as an exploit on a public issue** — even when the fix looks bounded. Supply-chain risk is out of scope entirely. Rationale: security findings carry disclosure, severity-rating, and backport concerns this member has no machinery for, and filing a public reproducing exploit _is_ disclosure — so the routing must withhold the repro from the public tracker, not merely change which queue files it.

8. **Cross-check each candidate against the tracker, and dedup across areas, before anything is filed.** DISPATCH runs an explicit **CROSS-CHECK** step after REPRODUCE and before CLASSIFY: the reproduced defect is checked against open issues and recently-merged fix PRs, and an already-tracked or already-fixed defect is annotated **already-known** and dropped citing the resolving issue/PR. Because areas are disjoint (Decision 2) intra-batch duplicates should not arise; FILE-AND-REPORT nonetheless runs a final cross-area candidate dedup as a backstop. Rationale: the member's whole value proposition is signal quality, and a duplicate-heavy filer is a spammer by another route.

9. **A clean area is a valid, valuable result.** An area whose hunt yields no reproducible defect is reported as **clean**, not as a failed run. Rationale: the incentive to manufacture a finding to justify the sweep is the exact failure mode the Iron Law exists to prevent; naming the clean outcome a success makes that incentive explicit and rejectable.

## Technical design

### Skill shape

A claude-code rigid skill at `agents/skills/claude-code/bug-fleet/` (`SKILL.md` plus `skill.yaml`), orchestrator-tier (`tier: 2`, `cognitive_mode: systematic-orchestrator`), with a domain-specific `## Rationalizations to Reject`. Platform variants (codex, cursor, gemini-cli, antigravity) are generated. The skill body carries no internal roadmap/PR/issue numbers — the family spine and ADRs are cited by title only, so the shipped skill reads correctly in any adopter project.

### The loop — five phases (stage-specific detail only; the skeleton is the family spine)

1. **SELECT.** Compose `harness-hotspot-detector`, `get_critical_paths`, `harness-impact-analysis` / `compute_blast_radius`, a git-churn pass, `harness-test-advisor` coverage depth, and any bugs parked by `test-fleet` into **disjoint** areas within the confirmed size bound. Score by composite **churn × blast radius × critical-path membership × inverse coverage depth**, reusing `harness-roadmap-pilot`-style impact scoring so ordering is principled and reproducible. Riskiest first.
2. **CONFIRM.** One up-front human round: the ranked areas with their risk basis; the **pinned base SHA** the whole batch verifies against; the proposed concurrency (default 2, max ~3); the confirmed **bounded-safe vs risky/large** fix boundary; the **area-size bound** (default 40 files / 4,000 LOC); the **candidates-per-area cap** (default 8); and the per-candidate **reproduction-attempt budget** (default 2). The human approves or trims once. Only guaranteed touchpoint before review.
3. **DISPATCH.** One worktree-isolated subagent per confirmed area, each running the real per-area pipeline: **HUNT** (review machinery over the area's standing code, with the Decision-3 adaptations) → **REFUTE** (adversarial try-to-disprove pass; refuted candidates recorded with reasons) → **REPRODUCE** (`harness-tdd` authors a test that must be observably and deterministically RED against unmodified code; unreproduced ⇒ **discarded** here, never reaching VERIFY) → **CROSS-CHECK** (tracker dedup; already-known ⇒ dropped with citation) → **CLASSIFY** (bounded-safe / risky-large / security-routed) → **FIX** (bounded-safe only, via the real `harness-debugging`). Capped at the governor and at the candidates-per-area cap. An unforeseen fork parks that one area and reports it.
4. **VERIFY.** Independently, never by self-report: confirm the **pipeline-provenance** session artifacts exist; transplant the reproducing test onto the **pinned base SHA** and confirm an **assertion-level** failure (a compile/resolution error ⇒ rejected); confirm it passes on the branch with the rest of the suite green; confirm all-OS CI green on every fix PR. Verdicts: `verified-fix`, `verified-issue`, `security-routed`, `rejected` (retried once first).
5. **FILE-AND-REPORT.** Run the cross-area dedup backstop. Open one fix PR per verified bug (never merged); file each risky/large bug as an issue linking and quoting its `repro/<slug>` branch; report security-routed items to the human without publishing the exploit. Emit a one-row-per-item batch summary carrying each item's assumptions-made note, plus discarded-candidate and refuted-candidate counts with reasons, already-known drops citing the resolving issue/PR, and clean areas.

### Key seams and data

- **`Area`** record: source analyses, id/slug, files/module covered (disjoint, within the size bound), risk basis (churn, blast radius, critical-path membership, coverage depth), composite score, and any detected forks.
- **`Candidate`** record: area, description, originating reviewer, refutation verdict (`survived` | `refuted` + reason), reproduction verdict (`reproduced` + test path | `unreproduced` + attempts | `nondeterministic`), tracker cross-check (`novel` | `already-known` + resolving issue/PR), fix class (`bounded-safe` | `risky-large` | `security-routed`), provenance (session paths for the `harness-tdd` / `harness-debugging` runs).
- **Batch** record: the pinned base SHA, the confirmed governor and caps, and the per-area verdicts.
- **Reuses:** the detection/analysis skills for the queue; the review machinery for the hunt; `harness-tdd` for the reproducing test; `harness-debugging` for the fix; `harness-roadmap-pilot`-style scoring for ordering; the subagent worktree-isolation primitive for fan-out; `gh` for tracker cross-check, CI reads, PR and issue creation.
- **Concurrency governor** at 2 (default), max ~3 — the shared machine-storm limit.

### Integration Points

- **Entry Points** — A new claude-code skill `bug-fleet` (`harness skill run bug-fleet`) and its MCP `run_skill` mapping. No new CLI command, MCP tool, or route.

- **Architectural Decisions** — None new. `bug-fleet` consumes the already-ratified family ADRs by title: _Subagent worktree fan-out (vs the Workflow primitive) for -fleet execution_ and _The front-load / park-unforeseen interaction model for the -fleet family_. The reproduction-required bar is a member-local discipline expressed as the skill's Iron Law and Gates — it constrains this member's verification only, not the family contract — so it warrants no standalone ADR.
- **Knowledge Impact** — Reinforces the `-fleet` family concept in the graph with a new distinction: a **proactive** quality-queue member operating on standing code, whose verification pairs a pipeline-provenance artifact with an executable reproduction rather than a convergence re-scan or a CI signal alone.

## Success Criteria

- Given a confirmed batch of N risk-ranked areas, the fleet produces a tiered batch of **verified** items — fix PRs and filed issues — where **every** item carries a deterministic reproducing failing test.
- **Every verified item carries pipeline-provenance artifacts** (`harness-tdd`, and `harness-debugging` for fix items) under `.harness/sessions/<slug>/`; an item with no provenance is rejected as not having run the real pipeline.
- **No item is filed or PR'd without repro evidence.** A candidate that cannot be reproduced deterministically within the confirmed attempt budget is discarded and reported as discarded, never filed.
- Every fix PR's reproducing test is independently confirmed to fail with an **assertion failure at the pinned base SHA** (a compile/resolution failure is a rejection, not a pass) and to pass on the branch, with the rest of the suite green and CI green across all three OS plus enforce and harness.
- Every filed issue links and quotes a test-only `repro/<slug>` branch whose test is independently confirmed red at the pinned base SHA.
- There is **exactly one** up-front human decision round; no per-area interactive pauses except a genuinely-unforeseen fork parked to its own area.
- **Every emitted PR and issue carries an "assumptions made" note** (ranking basis, hunt scope, refutation calls, fix-class call).
- Risky/large fixes are **filed with their reproducing test, never auto-applied**; security-routed findings are **reported without a published exploit, never patched inline**.
- Already-known defects are **dropped and annotated citing the resolving issue/PR, not re-filed**; the batch summary also lists discarded and refuted candidates with reasons.
- An area with no reproducible defect is reported as **clean** — a valid outcome, not a failure.
- The skill **never auto-merges** a fix PR.
- It **degrades gracefully**: a missing analysis source, a non-reproducing candidate, or a single area's failed hunt is reported while the batch continues; a rejected item is retried at most once.
- Concurrency never exceeds the confirmed governor (default 2, max ~3), and no area exceeds the confirmed size bound or candidates-per-area cap.
- No item is marked verified on a subagent self-report — every verdict is backed by independently-checked provenance plus an independently re-run reproducing test plus, for fix PRs, CI.
- `harness skill validate bug-fleet` passes; the shipped body carries no internal roadmap/PR/issue numbers.
