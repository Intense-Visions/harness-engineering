## Goal

Wire the new tool into the two skill bodies: harness-verify DETECT consults `canary_discover_test_command` for the **test** command before its package.json/Makefile heuristics; harness-tdd RED gains a canary detect-and-offer branch (B') that preserves the Iron Law. Skill bodies are markdown only — no production code.

> **SHIPPED-body rule (hard constraint):** skill bodies must carry **no** internal issue/PR numbers (no `#913`, no PR refs). These files ship into adopter projects. Only the `docs/changes/**` plan/proposal may reference `#913`.

## Observable Truths (Acceptance Criteria)

1. harness-verify DETECT instructs consulting `canary_discover_test_command` for the **test** command before package.json/Makefile/convention heuristics, using it only when `status: available` with a resolved framework, and falling through **silently** otherwise.
2. harness-verify DETECT leaves lint and typecheck discovery unchanged (registry is test-only).
3. harness-verify gains one domain-specific `## Rationalizations to Reject` row about preferring registry truth over a familiar package.json script.
4. harness-tdd RED gains a detect-and-offer branch: probe canary; if degraded → freehand (one-line nudge in `prompt`); if available → offer `/canary-write-test` and `canary_recommend_framework` when no framework is configured; honor `autoCapture` (`prompt`/`auto`/`skip`).
5. harness-tdd RED explicitly preserves the Iron Law: a canary-authored test MUST be watched to FAIL for the right reason before GREEN.
6. harness-tdd gains one domain-specific `## Rationalizations to Reject` row about not trusting a generated test without watching it fail.
7. Neither skill body contains an internal issue/PR number.
8. `harness skill validate harness-verify` and `harness skill validate harness-tdd` exit 0.
9. `pnpm generate:plugin:check` exits 0 after regenerated plugin artifacts are committed.

### Task 1: Wire harness-verify DETECT to consult the registry first

**Depends on:** Phase 2 complete (`canary_discover_test_command` registered)
**Files:** `agents/skills/claude-code/harness-verify/SKILL.md`

1. In `### Phase 1: DETECT`, insert this paragraph immediately **before** the line `Auto-detect project commands by inspecting the project root:`:

```markdown
**Test command — consult the canary registry first.** Before the heuristics below, call the `canary_discover_test_command` MCP tool with the test files you have already detected and whether this is a CI context: `{ files: [<detected test files>], ci: <true in CI> }`. If it returns `{ status: "available" }` with a matching framework, use that framework's `command` as the **test** command — it is authoritative registry truth. If it returns `{ status: "degraded" }`, matches no framework, or you have no candidate test files, fall through to the heuristics below **silently** (no nudge — verify is a mechanical gate, not an interactive skill). This applies to the **test** command only; lint and typecheck always use the heuristics below. When the resolved framework conflicts with a runner already configured in `package.json`/`Makefile` (e.g. registry offers playwright but the project's `test` script runs vitest), prefer the project's configured runner — the registry breaks ties by its own ordering, which need not match this project.
```

2. Add one row to the existing `## Rationalizations to Reject` table (after the last row):

```markdown
| "Canary resolved a test command but the project's `package.json` test script looks more familiar, so I'll use that" | When `canary_discover_test_command` returns `available` with a resolved command and it does not conflict with a configured runner, that registry-truth command wins for the test check. Fall back to `package.json`/`Makefile` heuristics only when canary degrades, no framework matches, or the registry framework conflicts with the project's configured runner. |
```

### Task 2: Wire harness-tdd RED with the canary detect-and-offer branch

**Depends on:** Task 1 (independent content, but keeps skill edits serialized for clean plugin regen)
**Files:** `agents/skills/claude-code/harness-tdd/SKILL.md`

1. In `### Phase 1: RED — Write a Failing Test`, insert a new numbered step **between** step 2 ("Write the test file...") and step 3 ("Write ONE minimal test..."), renumbering the subsequent steps (the current 3→4→5→6 become 4→5→6→7):

```markdown
3. **Canary-aware authoring (detect-and-offer).** Before writing the test by hand, call the `canary_probe` MCP tool.
   - **If `degraded`** (canary absent / binary missing / bad output): author the failing test freehand exactly as today. In `prompt` mode, add a single one-line nudge that installing canary enables generated first tests; otherwise stay silent.
   - **If `available`:**
     - If no test framework is configured for the target, call `canary_recommend_framework` with a short description of the behavior under test and surface the recommendation.
     - Offer the `/canary-write-test` skill to author the failing test. Honor `autoCapture`: under `auto` (autopilot/headless) generate without prompting; under `prompt` offer the choice; under `skip` stay freehand silently.
   - **The Iron Law is unchanged.** However the test is authored — by hand or by canary — you MUST run it and watch it FAIL for the right reason (the "watch it fail" step below) before writing any GREEN code. The generation source never bypasses the RED contract.
```

2. Add one row to the existing `## Rationalizations to Reject` table (after the last row):

```markdown
| "Canary generated the failing test, so I can trust it and skip watching it fail" | Generation source does not change the RED contract. A canary-authored test MUST still be run and observed to FAIL for the right reason before GREEN, exactly like a hand-written one. An unwatched generated test can pass for the wrong reason — the whole point of RED is defeated. |
```
