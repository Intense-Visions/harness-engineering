# craft-fleet — ceiling-raising code-quality elevation sweep

**Status:** Draft · **Tier:** Large · **Type:** rigid skill (orchestrator)
**Family:** `-fleet` (a quality-queue member working alongside the core conveyor)
**Keywords:** fleet, orchestration, batch, craft, ceiling-raising, llm-judgment, elevation, taste-gate, tiered, fan-out, worktree, batch-review

## Overview

The harness has a complete **floor** and no way to harvest its **ceiling** at batch scale. `cleanup-fleet` works the entropy/hotspot queue — dead code, drift, structural risk — all of it rule-based and objective (evidence: `agents/skills/claude-code/cleanup-fleet/SKILL.md:54-61`). `bug-fleet` hunts latent defects behind a reproduction bar. `test-fleet` chases coverage. Every one of them acts on findings a machine can prove. Meanwhile eleven `-craft` skills — `naming-craft`, `code-craft`, `copy-craft`, `test-craft`, `spec-craft`, `docs-craft`, `knowledge-craft`, `api-craft`, `cli-ergonomics-craft`, `security-craft`, `harness-design-craft` — encode the taste that says whether working code is any _good_, and they are invoked one file at a time, by a human who already suspected something was mediocre. The judgment exists; nothing sweeps with it.

`craft-fleet` is the **ceiling twin of cleanup-fleet**. It sweeps the codebase with the craft skills, ranks what they find, and hands back a **tiered** batch: bounded, high-confidence polish arrives as **elevation PRs**; larger structural quality debt is **filed as roadmap items** for the normal pipeline to build later. It is a **quality-queue** member of the `-fleet` family — it does not sit on the core intake → decide → build → land spine but works the craft-finding queue alongside it, exactly as `cleanup-fleet` works the entropy queue it mirrors.

The defining constraint is that **craft findings are advisory LLM judgment, not blocking authority — by deliberate design** (evidence: `docs/knowledge/decisions/0019-3-axis-craft-output-model.md`, whose whole premise is that craft findings are not binary and carry visible confidence). A fleet that autonomously rewrites subjective "low quality" across a codebase produces churn, style-thrash, and bulk PRs that are miserable to review — it would spend the human's attention rather than save it, which inverts the entire point of the family. So `craft-fleet` leans **file-don't-rewrite** for anything structural, reserves direct PRs for safe, bounded, high-confidence polish, and strengthens the human-taste gate beyond every sibling's: its CONFIRM round shows the human **real sample critiques**, not just counts, so taste is calibrated _before_ a sweep is authorized. This is the strategy's own division of labor — humans own the thinking layer, the harness mechanically polices below it (evidence: `STRATEGY.md#our-approach`) — applied to taste.

It also completes a named strategic track. `STRATEGY.md#tracks` commits to "Ceiling-raising via LLM judgment: add craft-pipeline skills that critique _quality_ … beyond what rule-based linters can catch." Eleven such skills now exist. `craft-fleet` is what turns that inventory into delivered elevation at batch scale.

### Goals

- Turn a craft-skill sweep of the codebase into a **tiered** batch — elevation PRs for bounded high-confidence polish, filed roadmap items for structural quality debt — with a single up-front human touchpoint plus one batch review.
- Hold a **cited-and-net-better** bar so no change is made on the orchestrator's own taste and no change ships that a re-critique cannot show as an improvement.
- Dogfood the real per-item pipeline (the craft skills for critique, `harness-refactoring` for the bounded elevation) — never hand-implement or short-cut it, and prove it ran by the artifacts it necessarily leaves behind.
- Compose the eleven craft skills rather than reimplementing critique, and derive the elevate-vs-file boundary from **their own** 3-axis output rather than inventing a second severity vocabulary.
- Protect the human's attention on both sides: never dump a low-value nit backlog into the tracker, and never emit a bulk PR that mixes kinds of judgment.
- Never auto-merge; the human lands the batch (optionally via `pr-fleet`).

### Non-goals (YAGNI)

- Auto-merging elevation PRs.
- Autonomously applying **any** structural quality change — cross-module reach, public-API or observable-contract change, module splits, abstraction redesign. These are filed, always.
- Reimplementing craft critique, rubric catalogs, or the 3-axis finding vocabulary — all eleven craft skills already exist and are catalog-driven.
- Depending on the `craft-pipeline` orchestrator, which is not built. `craft-fleet` composes the individual craft skills directly and gains nothing it would have to give back if that orchestrator later lands.
- Absorbing the broader docs / design / knowledge / performance quality-sweep candidates that remain open as backlog. `craft-fleet` sweeps **craft-skill findings**; scope expansion beyond that is a separate decision.
- Correctness work. A craft finding that turns out to be a real bug is **routed**, not fixed here — proving a defect requires a reproduction, which this member has no machinery for.
- A persisted "declined finding" suppression store. Recurrence is handled by the same tracker/PR cross-check every sibling runs; a second memory is speculative.
- Building a physical shared `-fleet` library — the shared contract is documented in `docs/reference/fleet-family.md`, not extracted into code.

## Decisions made

1. **Build on the documented family spine; define only the stage-specific parts.** `craft-fleet` reuses the shared five-phase skeleton (SELECT → CONFIRM → DISPATCH → VERIFY → terminal), the concurrency governor, the artifact + all-OS-CI verification discipline, the worktree fan-out with its nested-path push caveat, the one-up-front-CONFIRM / park-unforeseen interaction model, and the never-silent-merge invariant — all stated once in `docs/reference/fleet-family.md` (evidence: `docs/reference/fleet-family.md:15-53`). The `SKILL.md` cites that page rather than restating it, and defines only what is `craft-fleet`'s own: its queue, its elevate-vs-file taxonomy, its cited-and-net-better verification, its dual terminal act, and its domain-specific rationalizations.

2. **Queue: craft findings over coherent targets, produced by composing the eleven craft skills — reimplement no critique.** SELECT runs the craft skills the human enables over the repository and folds their findings into **targets**. A **target** is one coherent scope — a module, a doc set, a spec set — paired with **one craft domain**. Craft skills already discover their own corpora (evidence: `agents/skills/claude-code/code-craft/SKILL.md:22-27`) and emit structured findings each carrying `cite.rubricId` (`:62`), under a `runId` reported once per run in the run summary (`:80`), so the fleet's job is composition and ranking, not detection. A finding's cite is therefore **composed** — the run's `runId` paired with that finding's `rubricId` and location — rather than read off the finding alone. Missing or erroring craft skills degrade to the remaining ones and are recorded, never aborting the batch; if none is available there is nothing to rank and the fleet stops and reports.

3. **Ranking: severity × impact, read off the craft skills' own 3-axis output.** Every craft skill emits `tier` (`foundational` | `polish` | `aspirational`) × `impact` (`small` | `medium` | `large`) × `confidence` (`high` | `medium` | `low`) per ADR 0019 (evidence: `docs/knowledge/decisions/0019-3-axis-craft-output-model.md`). Ranking composes tier × impact, with confidence used as the routing axis in Decision 5 rather than folded into the score, and `harness-roadmap-pilot`-style impact scoring supplies the ordering discipline. Rationale: ADR 0019 exists precisely because collapsing these axes destroys the information a reviewer needs to prioritize; a fleet that invented its own severity scale would be re-collapsing them and would drift from the catalogs it consumes.

4. **A noise floor and a hard cap — and the cap, not the floor, is the real guard.** Eleven judgment skills swept across a whole repository produce a large tail of small observations. Two mechanisms bound it, and the spec is deliberate about which one does the work:
   - **The floor** drops, counts, and never files or elevates any finding whose `impact` is `small` **and** which is additionally either `tier: aspirational` **or** `confidence: low` — that is, `small` ∧ (`aspirational` ∨ `low`), with the grouping explicit so the rule cannot be read as `(small ∧ aspirational) ∨ low`. It removes the obvious tail cheaply.
   - **The cap** is the guard that actually holds. Filing goes through `manage_roadmap`, which opens a tracking issue per item — so an uncapped sweep is a tracker flood no floor can prevent, because the surviving `medium`-confidence middle of the distribution is large and legitimately routes to `file`. Per-batch caps are therefore hard: **20 filed items, 20 elevation PRs** by default, enforced after ranking so the cap keeps the highest tier × impact and drops the rest **as over-cap, reported with its count** — never silently. The caps count **emitted items** — elevation PRs and filed items — never findings, per the re-forming rule in Decision 5. They bound **SELECT-time intake**; a target that later downgrades from `elevate` to `file` converts an already-budgeted elevation slot rather than adding new intake, so a batch never hands back more items than the two caps together allow.

   Both the floor rule and the over-cap count appear in the batch summary, and both are re-tunable at CONFIRM. Rationale: a filer that turns every nit into a tracked item is a backlog spammer that costs more attention than it saves — the same failure mode `bug-fleet` guards with its reproduction bar, arriving here by a different route. Claiming the floor alone prevents that would be overselling a five-cell rule against a 27-cell distribution.

5. **Iron Law — CITED-AND-NET-BETTER, with a mechanical elevate-vs-file boundary in front of it.** No line is rewritten without a **cited craft finding** (`runId` + `rubricId` + location from an actual craft-skill run), and nothing is emitted that a **re-critique** does not show as net better. Routing is mechanical, on the finding's own axes plus a surface rule, never on how bad the finding feels:
   - **`elevate`** (direct PR) requires **all** of: `confidence: high`; the change is confined to one target and is behavior-preserving; no public-API, observable-contract, or exported-identifier change; no cross-module reach; and the finding's surface is on the **elevation-eligible list** for its domain (Decision 6).
   - **`file`** (roadmap item) — everything else that clears the noise floor: any structural change, any contract-touching change, any `medium`/`low`-confidence finding, and every finding in a file-only domain.
   - **`route`** — the finding is really a correctness defect or a genuine security vulnerability. Routing is **park-and-hand-back, not a new mechanism**: the item is parked, is neither elevated nor filed by this fleet, and is surfaced in the batch report — a correctness candidate as a **seed candidate for the correctness queue** (the precedent `test-fleet` set when it parks suspected bugs and hands them back rather than routing them itself), a security finding **privately to the human**, never opened as a public item. Rationale: this fleet cannot demand a reproduction and has no disclosure machinery, and filing a security finding publicly _is_ disclosure — so the routing must withhold, not merely redirect.

   **Routing is per finding; the targets are then re-formed by verdict.** The rules above read a finding, not a target, so a `(scope, domain)` pair whose findings split across verdicts never becomes a mixed target: it yields **at most one `elevate` target and at most one `file` item** for that same scope and domain, each carrying **only its own findings**, with routed findings leaving the pair entirely to be parked. That re-forming is what makes the downstream unit unambiguous — DISPATCH runs over one `elevate` target's findings plural, VERIFY assigns exactly one verdict per emitted item, and the caps in Decision 4 count emitted items rather than findings.

   Rationale: the craft skills are advisory by design, so the fleet must not convert advice into authority. Making the boundary mechanical — high confidence, bounded, behavior-preserving, eligible surface — keeps it from degrading into "this rewrite felt safe," which is exactly how a taste-driven fleet becomes a churn engine.

6. **Domain routing: elevation eligibility requires a surface the test suite guards.** The whole safety envelope of the elevation pipeline (Decision 7) is the test suite plus `harness check-deps` — those are what make "behavior-preserving" a checkable claim rather than an assertion. That yields one eligibility rule, not eleven judgment calls: **a surface is elevation-eligible only if it lives inside source the test suite exercises** — plus one narrower special case for test files themselves, which are the suite rather than exercised by it, and which qualify only under the assertion-freeze rule stated below the table. Everything else is file-only, and only four of the eleven domains clear the bar:

   | Craft domain           | Elevation-eligible surface                                                           | Otherwise    |
   | ---------------------- | ------------------------------------------------------------------------------------ | ------------ |
   | `naming-craft`         | Non-exported local identifiers only                                                  | file         |
   | `code-craft`           | Within-unit simplification and control-flow honesty, signature unchanged             | file         |
   | `copy-craft`           | **Internal-facing prose only** — code comments and internal log lines                | file         |
   | `test-craft`           | Test names and test-body clarity, **every assertion expression byte-identical**      | file         |
   | `docs-craft`           | Nothing — prose has no test suite to guard it                                        | file         |
   | `knowledge-craft`      | Nothing — prose has no test suite to guard it                                        | file         |
   | `spec-craft`           | Nothing — prose has no test suite to guard it; a ratified ADR is never edited at all | file         |
   | `harness-design-craft` | Nothing — no craft-driven write path exists                                          | file         |
   | `api-craft`            | Nothing — every surface it critiques is a published contract                         | file         |
   | `cli-ergonomics-craft` | Nothing — every surface it critiques is a published contract                         | file         |
   | `security-craft`       | Nothing — **never elevated**                                                         | file / route |

   Rationale, domain by domain. **Prose domains** (`docs-craft`, `knowledge-craft`, `spec-craft`) were the tempting case and are cut deliberately: no skill in the toolset applies prose-quality edits under a safety envelope — `align-documentation` syncs docs to code drift, not prose quality — so elevating prose would mean the orchestrator free-hand rewriting text with no mechanical check that it did not make things worse, which is precisely the churn this member exists to avoid. A ratified ADR is additionally out of bounds on its own terms: it is a historical record of a decision, not a document to be improved, and editing one rewrites the past. **`api-craft` and `cli-ergonomics-craft`** critique **published contracts** by definition — renaming a flag or an endpoint is a breaking change wearing a quality argument. **`security-craft`** is never auto-applied because a wrong "improvement" to security posture is worse than the mediocrity it replaced. **`harness-design-craft`** has no reachable write path: its POLISH phase emits before/after sketches and explicitly never modifies source (evidence: `agents/skills/claude-code/harness-design-craft/SKILL.md:69`), and `align-design-system` — the obvious candidate — consumes `DRIFT-*` findings from the rule-based `detect-design-drift` floor, which carry no craft `runId`/`rubricId`, so a token codemod could never satisfy the Iron Law's cite requirement. Wiring the two together would mean inventing a finding translation the Iron Law exists to forbid.

   `copy-craft`'s eligibility is narrowed for a reason worth stating, because it establishes the general principle: **routing follows the surface, not the skill that surfaced the finding.** An error message and a CLI output string are the same bytes on the user's screen whether `copy-craft` or `cli-ergonomics-craft` found them, so they get the same treatment — **filed**, because user-facing output is an observable contract and Decision 5 bars elevating any contract-touching change regardless of which domain raised it. What remains elevation-eligible is genuinely internal: **code comments**, which cannot alter behavior at all and are therefore the safest edit in the codebase, and **internal log lines**, which are diagnostic output no consumer depends on. Yes, this shrinks the elevation surface; that is the direction this member is designed to err in.

   `test-craft`'s eligibility is deliberately narrower than it first reads. The elevation pipeline proves behavior preservation **with** the test suite, so elevating tests is circular unless the change provably cannot alter what the suite checks. The rule that breaks the circle is mechanical: every assertion expression must be **byte-identical** before and after, the **passing-test count must be unchanged**, and the set of passing test IDs may differ **only by the renames the elevation itself applied** — a rename changes a test's ID by construction, so freezing the ID set outright would forbid the very change this row exists to permit. Renaming a test or clarifying its arrange/act body qualifies; "sharpening an assertion" does not, because sharpening an assertion changes what is asserted — that is a `file`.

7. **The per-item elevation pipeline is the real `harness-refactoring`.** Every craft skill is judgment-only and writes nothing — each ships a "No autofix" gate (evidence: `agents/skills/claude-code/code-craft/SKILL.md:18` — "NOT for autofix / refactoring (this is judgment-only)"; `agents/skills/claude-code/naming-craft/SKILL.md:234` — "No autofix. This is ceiling-judgment."; `agents/skills/claude-code/harness-design-craft/SKILL.md:69` — POLISH "never modifies source"). The craft family therefore supplies the finding, and the elevation must be driven by a skill whose job is behavior-preserving change under validation. `harness-refactoring` is exactly that: tests green before and after **every** change, `harness validate` + `harness check-deps` per step, blast-radius computed up front, one small change per commit, and — decisively — "if the refactoring introduced no improvement, revert the entire sequence; refactoring for its own sake is churn" (evidence: `agents/skills/claude-code/harness-refactoring/SKILL.md:21`, `:31`, `:60-79`, `:102`). The anti-churn discipline `craft-fleet` needs is already law inside the skill it composes. Composing it also inherits its precondition, which is broader than the suite alone: `harness-refactoring` refuses to run against a failing suite (evidence: `:15`, `:21`) **and** requires a baseline `harness validate` plus `harness check-deps` that both pass before the first step (evidence: `:31`). Elevation therefore **assumes a clean baseline at the pinned base SHA on all three**; a target whose baseline is not clean does not elevate — it takes the same downgrade-to-`file`-and-report path a mid-flight structural discovery takes. It is the **only** elevation pipeline — there is no second path for design tokens or prose (Decision 6). Rationale: composing an existing safety envelope beats authoring a second one, and the step-granular commit trail it mandates is half the evidence VERIFY needs.

8. **Verification: three independent proofs — critique provenance, elevation provenance, and net-improvement — plus all-OS CI green, never a self-report.** No single artifact covers the fleet's two distinct risks (an agent applying its own taste, and an elevation that makes things worse), so VERIFY checks all three per **elevation** (the `file` tier is verified here too, but to the narrower standard stated at the end of this decision, because it never produced a branch):
   - **Critique provenance** — every changed location maps to a cited finding from a real craft-skill run (`runId` + `rubricId`). A change with no cited finding is the orchestrator's own taste and is **rejected**, however good it looks. This is the ceiling analogue of `bug-fleet`'s reproduction bar: the cite is the thing that cannot be produced by asserting it.
   - **Elevation provenance** — the step-granular `harness-refactoring` commit trail on the branch: one structural change per commit, suite green throughout. Absent trail = the real pipeline did not run = rejected.
   - **Net-improvement evidence** — the ceiling analogue of `cleanup-fleet`'s convergence re-scan: re-run **the same craft skill** over the changed scope on the branch and require that the cited findings are **resolved** _and_ **no new finding at equal-or-higher tier was introduced**. Tier ordering is the craft catalogs' own — `foundational` (fix-to-be-not-broken) outranks `polish`, which outranks `aspirational` — so "equal-or-higher" is evaluated mechanically rather than by feel. A re-critique that trades one finding for another is **style-thrash, not elevation**. A re-critique that cannot run at all — no LLM provider configured, a budget-exceeded prompt collection, an erroring skill — produces **no proof**, and by the same rule that rejects a missing commit trail the item is **rejected** and retried once, an unavailable provider usually being transient. That is deliberately a different outcome from the two runs _disagreeing_ (below), which downgrades rather than retries: a re-critique that never ran leaves nothing to re-examine, while one that ran and split has already produced its reading.

     **The oracle is non-deterministic, and the protocol says so.** A re-critique is an LLM call: two runs over identical code can disagree, so a single run can both falsely reject a good elevation and falsely accept a bad one. `bug-fleet` met the same problem and answered it explicitly (three runs, consistent red required, nondeterministic ⇒ discarded); this member answers it with a **two-run protocol biased conservative on both sides**:
     - A cited finding counts as **resolved only if it is absent from both runs**. Unanimity is required to credit an improvement.
     - A new equal-or-higher-tier finding **blocks if it appears in either run**. One sighting of a regression is enough to stop shipping the rewrite.
     - When the two runs disagree, the elevation is **not proven** — but the underlying critique is still valid, so the item **downgrades to `file`** rather than being discarded. Nothing is lost; only the autonomous rewrite is withheld.

     **VERIFY owns both runs; the DISPATCH subagent runs none.** The family's hard invariant is that a verdict never rests on a subagent's self-report, and a subagent that runs its own re-critique and reports the outcome is exactly that — the orchestrator would be reading a claim, not checking a proof. Having both re-run would satisfy the invariant but cost four runs per item. Concentrating both runs in VERIFY keeps the total at two _and_ makes them independent, so the cost rationale and the invariant are satisfied by the same choice rather than traded against each other. The subagent's job ends at pushing a branch with its commit trail and its cited findings.

     Two runs rather than three is a deliberate cost call — craft skills bill per LLM call and this fleet runs eleven of them across a repository — and the downgrade-not-discard fallback is what makes the cheaper protocol safe: an inconclusive oracle costs the batch a filed item, never a bad merge.

   Plus behavior preservation (the passing-test count does not decrease, no public-API or observable-contract change) and CI green on all three operating systems plus the enforce and harness checks. A rejected item is retried once; still failing, it is reported as rejected and the batch continues.

   **The `file` tier is verified to its own, narrower standard.** A `file` item never enters DISPATCH, so it has no branch, no commit trail, no re-critique, and no CI — four of the checks above have nothing to read, and scoping them to elevations is what keeps the `verified-filing` verdict meaningful rather than vacuous. `verified-filing` requires exactly two things: **critique provenance**, the cite resolving to a real craft-skill run (`runId` + `rubricId` + location) exactly as an elevation's must, and the **cross-check**, confirming at verification time that the target is still not already addressed by an open elevation PR or an existing filed item. An item that fails either is **rejected rather than filed** — those two are the only claims a filing actually makes, and a stale cite or a duplicate filing costs the human precisely the attention this fleet exists to save.

9. **Terminal act: TIERED and dual — elevation PRs plus filed roadmap items, batched homogeneously.** Verified `elevate` items become PRs; verified `file` items become roadmap items (each carrying its cited finding, its rubric, and its location so the eventual builder does not re-derive the critique). Elevation PRs are batched **one per (target, craft domain)** — never one per finding, never mixed across domains. Rationale: `bug-fleet`'s one-PR-per-bug granularity is right when each item is a distinct defect, but forty naming fixes as forty PRs is a denial-of-service on review, and forty mixed fixes in one PR forces the reviewer to switch judgment modes line by line. Homogeneous batching gives the reviewer **one kind of taste question at a time over one coherent scope**, which is the only shape in which bulk taste review is actually tractable.

10. **The taste gate is strengthened, because taste does not generalize.** Every sibling's CONFIRM presents a ranked batch. `craft-fleet`'s additionally presents a **taste-calibration sample** — a handful of real, verbatim findings, elevation and file alike, drawn from the actual critique run — plus the **craft-domain selection** (which of the eleven skills run at all) and the noise-floor and cap settings. Rationale: counts tell a human how much work is proposed; only a sample tells them whether this sweep's taste matches theirs, and that is the question on which the whole batch's value turns. It is also the cheapest possible place to discover a mismatch — before fan-out rather than at review.

11. **A quiet target is a valid, valuable result.** A target whose critique yields nothing above the noise floor is reported as **quiet**, not as a failed run. Rationale: the incentive to manufacture an elevation so a sweep does not look wasted is the precise failure mode a subjective-judgment fleet must design against; naming the quiet outcome a success makes that incentive explicit and rejectable.

## Technical design

### Skill shape

A claude-code rigid skill at `agents/skills/claude-code/craft-fleet/` (`SKILL.md` plus `skill.yaml`), orchestrator-tier (`tier: 2`, `cognitive_mode: systematic-orchestrator`), with a domain-specific `## Rationalizations to Reject`. Platform variants (codex, cursor, gemini-cli, antigravity) are generated. The skill body carries no internal roadmap/PR/issue numbers — the family spine and ADRs are cited by title only, so the shipped skill reads correctly in any adopter project.

### The loop — five phases (stage-specific detail only; the skeleton is the family spine)

1. **SELECT.** Run the enabled craft skills; fold their findings into `(scope, craft domain)` **targets**; apply the **noise floor**; cross-check each target against open elevation PRs and already-filed quality items; route each surviving finding `elevate` / `file` / `route` by the mechanical boundary; score and order by tier × impact with `harness-roadmap-pilot`-style scoring. Missing craft skills degrade and are recorded.
2. **CONFIRM.** One up-front human round: the enabled **craft domains**; the ranked targets with their elevate/file split; the **taste-calibration sample** of verbatim findings; the **noise floor** and the per-batch caps; the proposed concurrency (default 2, max ~3); and the **pinned base SHA** the whole batch works against — the SELECT critique run is pinned to it so VERIFY's branch re-critique is a like-for-like comparison rather than a moving target across a multi-hour batch, and so the green-baseline precondition (Decision 7) is evaluated once for the batch. The human approves, trims, disables domains, or re-tunes the floor once. Only guaranteed touchpoint before review. `--dry-run` stops here.
3. **DISPATCH.** One worktree-isolated subagent per confirmed **elevate** target, each running the real `harness-refactoring` pipeline over its one target's cited findings and pushing a branch carrying its commit trail and its cites. It runs **no re-critique** — that proof belongs to VERIFY (Decision 8). `file` targets require no fan-out. A target whose elevation turns out to need a structural change, or whose baseline is not clean at the pinned base (a red suite, or a failing `harness validate` or `check-deps`), **downgrades itself to `file` and reports** rather than applying it. Capped at the governor and the per-batch caps. An unforeseen fork parks that one target.
4. **VERIFY.** Independently, never by self-report. For every **elevation**: **critique provenance** (every changed location cites a real finding), **elevation provenance** (the step-granular refactoring commit trail), **net-improvement** (both runs of the two-run re-critique protocol, executed here rather than read from the subagent — disagreement downgrades the item to `file`), behavior preservation, and all-OS CI green. For every **filing**, which has no branch and so no trail, re-critique, or CI: the narrower `verified-filing` standard of critique provenance plus the cross-check that the target is not already addressed (Decision 8). Verdicts: `verified-elevation`, `verified-filing`, `routed`, `downgraded`, `rejected` (retried once first).
5. **FILE-AND-REPORT.** Open one elevation PR per verified `(target, craft domain)` — never merged, each carrying its cited findings and an assumptions-made note. File each verified `file` item — including every target downgraded from `elevate`, whose critique remains valid even though its rewrite was withheld — as a roadmap item carrying its cite, rubric, and location, plus an **assumptions-made note the orchestrator writes here** from SELECT's routing basis (the ranking basis, the routing call, and why it was filed rather than elevated). A downgraded target arrives carrying the note its subagent already wrote in DISPATCH; a pure-`file` item never had a subagent, so this is the phase that produces its note. Park-and-hand-back routed findings. Emit a one-row-per-item batch summary including dropped-by-noise-floor and over-cap counts, downgraded targets with their downgrade reason, cross-check drops citing their resolving PR/item, and quiet targets.

### Key seams and data

- **`Target`** record: craft domain, id/slug, scope (files / docs / specs it covers), the findings it opens with (each with `runId`, `rubricId`, location, tier, impact, confidence), composite tier × impact score, routing verdict (`elevate` | `file` | `route`), cross-check (`novel` | `already-addressed` + resolving PR/item), and any detected forks.
- **`Finding` cite**: `runId` + `rubricId` + location — the unforgeable link back to an audited craft-catalog run; carried through DISPATCH, checked in VERIFY, and quoted in the PR or filed item.
- **Batch** record: enabled craft domains, pinned base SHA, confirmed noise floor, caps, governor, and per-target verdicts.
- **Reuses:** the eleven craft skills for the queue and for the re-critique; `harness-refactoring` as the single bounded-elevation pipeline; `harness-roadmap-pilot`-style scoring for ordering; the subagent worktree-isolation primitive for fan-out; `manage_roadmap` for filing; `gh` for cross-check, CI reads, and PR creation.
- **Concurrency governor** at 2 (default), max ~3 — the shared machine-storm limit.

### Integration Points

- **Entry Points** — A new claude-code skill `craft-fleet` (`harness skill run craft-fleet`) and its MCP `run_skill` mapping. No new CLI command, MCP tool, or route.
- **Registrations Required** — Skill discovery regeneration: `harness generate` regenerates the plugin command directories, `docs/reference/skills-catalog.md`, and the platform variants (codex, cursor, gemini-cli, antigravity). A roadmap shard `docs/roadmap.d/craft-fleet.md` registers the member in the family milestone, and the `docs/roadmap.md` aggregate is regenerated from it.
- **Documentation Updates** — Add `craft-fleet`'s row to the Members table in `docs/reference/fleet-family.md` and name it in that page's conveyor sentence alongside the other quality-queue members. Add the roadmap shard described above. No other doc edits beyond the generated catalog.
- **Architectural Decisions** — None new. `craft-fleet` consumes the already-ratified family ADRs by title: _Subagent worktree fan-out (vs the Workflow primitive) for -fleet execution_ and _The front-load / park-unforeseen interaction model for the -fleet family_, and consumes the craft output vocabulary from _3-axis (tier × impact × confidence) output model_ without extending it. The cited-and-net-better bar and the elevation-eligibility table are member-local disciplines expressed as this skill's Iron Law, routing table, and Gates — they constrain this member's verification only, not the family contract or the craft catalogs — so they warrant no standalone ADR.
- **Knowledge Impact** — Reinforces the `-fleet` family concept with a new distinction: a **ceiling** quality-queue member whose queue is advisory LLM judgment rather than rule-based findings, whose verification pairs a critique cite with a net-improvement re-critique, and whose terminal act is deliberately asymmetric — bounded polish is applied, structural taste debt is handed back to the human thinking layer.

## Success Criteria

- Given a confirmed batch of N craft targets, the fleet produces a **tiered** batch: elevation PRs for verified bounded polish and filed roadmap items for verified structural quality debt, with **every** item carrying a cited craft finding (`runId` + `rubricId` + location).
- **No line is changed without a cited craft finding.** A changed location that maps to no finding from a real craft-skill run is rejected as the orchestrator's own taste.
- **Every elevation PR carries the step-granular `harness-refactoring` commit trail** (one structural change per commit); an item with no such trail is rejected as not having run the real pipeline.
- **Every elevation is confirmed net better by a two-run re-critique that VERIFY itself executes** — never by a re-critique the dispatch subagent ran and reported. Each cited finding is absent from **both** runs, and **no** run reports a new finding at equal-or-higher tier (`foundational` > `polish` > `aspirational`). A re-critique that trades one finding for another is style-thrash and does not ship; two runs that disagree leave the elevation unproven and the item **downgrades to `file`**; a re-critique that could not run at all is rejected for want of proof, never passed.
- Every elevation PR preserves behavior — the passing-test count does not decrease and no public-API or observable-contract change is present — and is green across all three OS plus enforce and harness.
- **No structural quality change is ever auto-applied.** Cross-module reach, contract change, exported-identifier change, module splits, and abstraction redesign are filed, always — including when a target discovers mid-flight that its elevation requires one, in which case it downgrades to `file` and reports. A target whose baseline is not clean at the pinned base SHA — a red suite, or a failing `harness validate` or `check-deps` — takes the same downgrade path, since those three checks together are the elevation pipeline's safety net.
- **Only `naming-craft`, `code-craft`, `copy-craft`, and `test-craft` ever produce an elevation.** The other seven domains are file-only: no prose file, no design token, no API or CLI contract surface, and no `security-craft` finding is ever rewritten by this fleet, and a ratified ADR is never edited at all.
- **User-facing output is never elevated, whichever domain surfaced it.** A `copy-craft` finding on an error message or a CLI output string is filed on the same terms as a `cli-ergonomics-craft` finding on the same bytes; only internal-facing prose — code comments and internal log lines — is elevation-eligible.
- **A `test-craft` elevation leaves every assertion expression byte-identical** and the passing-test count unchanged, with the passing test-ID set differing only by the renames the elevation itself applied; anything that changes what a test asserts is filed.
- Findings below the noise floor (`impact: small` **and** (`tier: aspirational` **or** `confidence: low`)) are **dropped and counted, never filed**; the per-batch caps (default 20 filed, 20 elevation PRs) are never exceeded, and everything the cap sheds is **reported as over-cap with its count**, never silently dropped.
- There is **exactly one** up-front human decision round, and it presents a **taste-calibration sample of verbatim findings** alongside the domain selection, the noise floor, and the caps — not counts alone.
- **Every emitted PR and filed item carries an "assumptions made" note** (ranking basis, routing call, elevation scope, what was deliberately left un-elevated).
- Elevation PRs are batched **one per target** — and since a target is by definition one scope paired with exactly one craft domain (Decision 2), that means **never one PR per finding, and never two craft domains in one PR**. Both failures are observable from the emitted PR set.
- Findings that are really correctness defects or security vulnerabilities are **routed** — parked, neither elevated nor filed by this fleet, and handed back in the batch report: correctness candidates as seed candidates for the correctness queue, security vulnerabilities privately to the human, never patched inline and never published to a public tracker. (Ordinary `security-craft` posture findings that are not vulnerabilities take the `file` path like any other file-only domain — see Decision 6.)
- Already-addressed targets are **dropped and annotated citing the resolving PR or item, not re-elevated**.
- A target with nothing above the noise floor is reported as **quiet** — a valid outcome, not a failure.
- The skill **never auto-merges** an elevation PR.
- It **degrades gracefully in SELECT and DISPATCH**: a missing or erroring craft skill, a downgraded target, or a single target's failed elevation is reported while the batch continues; a rejected item is retried at most once. Degradation never reaches VERIFY — a proof that phase's standard for the item's tier demands and cannot produce is a rejection, not a graceful skip.
- Concurrency never exceeds the confirmed governor (default 2, max ~3).
- **No item is marked verified on a subagent self-report.** Every **elevation** verdict is backed by independently-checked critique provenance, elevation provenance, a re-run critique, and all-OS CI; every **filing** verdict — which has no branch to check — is backed by its cite resolving to a real craft-skill run and by a cross-check that the target is not already addressed.
- `harness skill validate craft-fleet` passes; the shipped body carries no internal roadmap/PR/issue numbers.
