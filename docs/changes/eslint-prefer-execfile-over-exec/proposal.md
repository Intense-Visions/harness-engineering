# ESLint Rule: prefer-execfile-over-exec

## Overview & Goals

Add a new ESLint rule, `@harness-engineering/prefer-execfile-over-exec`, to
`packages/eslint-plugin`. It flags `child_process.exec` / `execSync` calls made
with a **string command** — which spawn a `/bin/sh` and interpolate the string —
and steers authors toward `execFile` / `execFileSync` with an **array of args**,
which never involves a shell.

**Why:** string-command `exec` is the primary shell-injection surface in a
Node codebase and silently mishandles exit codes when the command contains shell
redirects/pipes. The array-arg `execFile` form removes the shell entirely.
The roadmap item (#222) notes 15+ instances in this codebase.

**Goal:** a precise, low-false-positive lint rule that reports (does not
auto-fix) string-command `exec`/`execSync` usage, shipped as a sibling to the
existing `no-unix-shell-command` rule.

## Decisions Made

1. **Report-only, no autofix.** Converting `exec('a b c')` to
   `execFile('a', ['b','c'])` requires shell tokenization (quoting, globs, pipes),
   which cannot be done safely by a mechanical fixer. Matches the report-only
   posture of the sibling rules `no-unix-shell-command` and `no-process-exit`.
   _Rationale:_ a wrong autofix on a security-adjacent rule is worse than none.

2. **Detect on string-command first argument only** (string literal or template
   literal), reusing the `extractCommandString` helper pattern from
   `no-unix-shell-command`. `exec(someVariable)` is **not** flagged — the rule
   cannot verify the variable is a shell string, and staying literal-scoped keeps
   false positives near zero. _Rationale:_ the roadmap frames this as
   "exec with string commands"; conservative scope matches the sibling rule.

3. **Guard against the `RegExp.prototype.exec` false positive.** `exec` as a
   member call is ambiguous — `child_process.exec(...)` (flag) vs
   `myRegex.exec(str)` (must NOT flag). Resolution:
   - `execSync` — unambiguous (RegExp has no `execSync`): flag bare
     `execSync(str)` and any member `X.execSync(str)` with a string-command arg.
   - `exec` bare identifier — flag `exec(str)` with a string-command arg
     (destructured `child_process` import is the overwhelmingly common shape).
   - `exec` member `X.exec(...)` — flag **only** when the object identifier is a
     recognized child*process alias (`child_process`, `childProcess`, `cp`,
     `child`). This deliberately excludes `regex.exec(str)`.
     \_Rationale:* `.exec` on a regex is the dominant non-child_process `.exec` call;
     excluding it by object-name allowlist is the single most important
     false-positive guard.

4. **Enablement level.** Register in the plugin's `recommended` config as `warn`
   and `strict` config as `error`, mirroring `no-unix-shell-command`. Enable in
   this repo's own `eslint.config.js` as `warn`. _Rationale:_ 15+ existing
   instances mean `error` in the repo config would be noise/breakage; `eslint src`
   runs with no `--max-warnings`, so `warn` surfaces every instance without
   failing CI — the same migration posture used for `no-sync-io-in-async`.

5. **`meta.type: 'problem'`** — shell injection is a correctness/security defect,
   consistent with `no-unix-shell-command` and `no-process-exit`.

## Technical Design

**New file:** `packages/eslint-plugin/src/rules/prefer-execfile-over-exec.ts`

- Built with `ESLintUtils.RuleCreator` (same factory as every sibling rule).
- `type MessageIds = 'preferExecFile'`.
- Message: guidance to replace the string-command `exec`/`execSync` with
  `execFile`/`execFileSync` and an array of arguments (no shell).
- `create(context)` returns a `CallExpression` visitor implementing the
  Decision-3 detection matrix. Helpers mirror `no-unix-shell-command`:
  - `getExecCall(node)` → `'exec' | 'execSync' | undefined` applying the
    identifier/member + RegExp-guard logic.
  - `isStringCommand(arg)` → true for string `Literal` or `TemplateLiteral`
    (adapted from `extractCommandString`; presence, not value, is what matters).
- `schema: []`, `defaultOptions: []` — no configuration.

**Registration (mechanical):**

- `packages/eslint-plugin/src/rules/index.ts` — regenerated by
  `pnpm generate:rules` (auto-generated barrel; do not hand-edit).
- `packages/eslint-plugin/src/index.ts` — add the rule id to the `recommended`
  (`warn`) and `strict` (`error`) config rule maps.
- `eslint.config.js` (repo root) — add
  `'@harness-engineering/prefer-execfile-over-exec': 'warn'` to the harness-plugin
  rules block.

**New test:** `packages/eslint-plugin/tests/rules/prefer-execfile-over-exec.test.ts`
using `@typescript-eslint/rule-tester` (same harness as every sibling test).

## Integration Points

- **Entry Points:** new ESLint rule module in `packages/eslint-plugin/src/rules/`.
- **Registrations Required:** regenerate the rules barrel (`pnpm generate:rules`);
  add the rule to `recommended` + `strict` config maps in `src/index.ts`; enable
  as `warn` in the repo-root `eslint.config.js`.
- **Documentation Updates:** None required (the plugin has no per-rule
  `docs/rules/` directory; the RuleCreator doc URL is a naming convention only).
- **Architectural Decisions:** None — small change, no ADR.
- **Knowledge Impact:** None — reinforces the existing "prefer execFile over
  shell exec" pattern already embodied by `no-unix-shell-command`.

## Success Criteria

1. `prefer-execfile-over-exec.ts` exists, exported via the regenerated barrel, and
   appears in `rules` from `@harness-engineering/eslint-plugin`.
2. When lint runs on `exec('rm -rf dist')`, `execSync('tsc && cp a b')`,
   `child_process.exec(\`git \${x}\`)`, the rule reports `preferExecFile`.
3. When lint runs on `execFile('git', ['status'])`, `execFileSync('rm', ['-rf'])`,
   `myRegex.exec(input)`, `/ab+c/.exec(str)`, and `exec(dynamicVar)`, the rule
   reports **nothing** (no false positives).
4. The rule appears in the plugin's `recommended` (`warn`) and `strict` (`error`)
   configs and in the repo's `eslint.config.js` (`warn`).
5. New rule test passes; the full `packages/eslint-plugin` test + typecheck + lint
   suite stays green; repo lint does not newly fail (warnings only).

## Implementation Order

1. **Rule + tests.** Write `prefer-execfile-over-exec.ts` and its rule-tester
   spec (valid: execFile\*, regex.exec, dynamic-var exec; invalid: string-command
   exec/execSync in bare + child_process-member forms). Run the package tests.
2. **Register.** `pnpm generate:rules` to refresh the barrel; add to `recommended`

3. **Verify.** Package build + test + typecheck + lint green; run repo lint to
   confirm existing `exec` instances surface as warnings, not errors.
