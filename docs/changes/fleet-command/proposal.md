# fleet-command — the conductor coordinating the `-fleet` family across the SDLC

**Status:** Draft · **Tier:** Large · **Type:** rigid skill (conductor / orchestrator-of-orchestrators)
**Family:** `-fleet` — the **conductor tier above** the members; deliberately not named `-fleet`
**Keywords:** conductor, fleet-coordination, dependency-dag, global-governor, machine-storm, conflict-serialization, merge-order, wave-gating, bounded-run, consolidated-report, never-auto-merge

## Overview

Eleven `-fleet` skills now exist. Each one is a competent, self-contained orchestrator over a single SDLC work-queue: `ideate-fleet` ranks opportunity, `issue-fleet` triages intake, `adr-fleet` drafts decisions, `roadmap-fleet` builds, `pr-fleet` lands, and `cicd-fleet`, `test-fleet`, `security-fleet`, `cleanup-fleet`, `bug-fleet`, `craft-fleet` work quality queues alongside (evidence: `docs/reference/fleet-family.md:65-79`, the Members table). What does not exist is anything that can run **more than one of them in the same session** without the operator personally holding the whole shape in their head.

That gap has three concrete costs, and each is a failure the family's own invariants cannot reach from inside a single member.

**The fan-out² problem.** Each member caps concurrent subagents at 2 (default), max ~3 — the machine-storm limit, stated once for the family precisely because exceeding it produces flaky failures indistinguishable from real ones (evidence: `docs/reference/fleet-family.md:47-49`). That cap is **per fleet**. Nothing enforces it _across_ fleets. Two fleets running at their own caps is 6 concurrent build agents; a naive "run the maintenance sweeps in parallel" is 18. Every member is individually well-behaved and the aggregate is a machine-storm generator. A cap that each participant honors locally and no one enforces globally is not a cap.

**The dependency problem.** The conveyor is a real dependency chain, not a menu: `issue-fleet` produces the ranked, routed queue `adr-fleet` and `roadmap-fleet` consume; `pr-fleet` lands what the others produced (evidence: `docs/reference/fleet-family.md:13`, the conveyor sentence). Running them concurrently means each consumes its predecessor's _stale_ output. Running them all serially wastes the genuine parallelism of the quality sweeps, whose **inputs** are independent of the spine and of each other — though several of their **outputs** file back into intake's queue, which is a real edge and is handled explicitly rather than ignored (Decision 4). The correct shape is a hybrid DAG, and deriving it correctly every session is exactly the kind of held-in-the-head coordination the family exists to remove.

**The collision problem.** Fleets write shared artifacts. Adding a skill regenerates `docs/reference/skills-catalog.md`, the four platform command manifests, and the roadmap aggregate; ADR numbers are allocated from one sequence; roadmap shards land in one directory. Sibling PRs from a single batch already conflict on these and require a manual serial-merge-with-regeneration playbook — observed first-hand across two consecutive family batches. Multiply that by concurrent fleets and the merge tax scales with the square of the parallelism the conductor was supposed to buy. And a fourth class no single fleet can see at all: `bug-fleet`, `security-fleet`, `test-fleet`, and `craft-fleet` each file items, and each is blind to the others — one defect can arrive as four tracker items, each individually correct.

`fleet-command` is the **conductor**: one tier above the fleets, coordinating the fleets themselves rather than fanning out over an item-queue. It plans a run as a dependency DAG, enforces one **global** budget across every fleet in flight, serializes the fleets whose outputs would collide, batches the members' human gates into a few coherent rounds instead of eleven scattered interruptions, and emits one consolidated report. It is the family **capstone**, and it is built last by construction — it composes members that must already exist.

Its authority is deliberately **coordinator plus global governor, never dictator**: it owns scheduling, the budget, deconfliction, and reporting, but **each fleet keeps its own human CONFIRM gate**, and it **never auto-merges**. Coordinated, not collapsed. This is the strategy's own division of labor — humans own the thinking layer, the harness mechanically polices everything below it (evidence: `STRATEGY.md#our-approach`) — applied one level up: the conductor mechanizes the _scheduling and safety_ of a multi-fleet run and mechanizes none of the _judgment_ inside it.

### Goals

- Enforce **one global concurrency budget** across every fleet in flight, so a multi-fleet run is bounded by the same machine-storm limit a single fleet is — never by the sum of per-fleet governors.
- Plan the run as a **hybrid dependency DAG**: a CI **trust gate** ahead of everything, then the conveyor spine sequential by dependency with the quality sweeps parallel alongside, and the land stage terminal — with no dependency edge inside any wave.
- Own **cross-fleet deconfliction**: serialize fleets whose emissions provably collide, sequence regeneration, produce a merge-order plan, and dedup filed items across fleets.
- **Coordinate** the human gates — one run-plan authorization plus one batched gate round per DAG wave — without removing any fleet's own CONFIRM.
- Keep the run **bounded**: a hard budget, one pass per fleet, a cap on fleets per run, and a partial report on exhaustion rather than an open-ended loop.
- Verify each fleet lane by its **emitted artifacts**, never by a fleet's self-report, and hand back **one consolidated report**.
- **Never auto-merge**, and never override or answer a member's own gate.

### Non-goals (YAGNI)

- **Merging anything.** The conductor's merge-order plan is a _recommendation_ attached to its report and handed to `pr-fleet` / the human. It never merges, and it never authorizes `pr-fleet` to land on the human's behalf.
- **Collapsing the members' CONFIRM gates into one.** Batching gates by wave is scheduling; answering them is not. A fleet's taste-check is that fleet's, and the human's.
- **Re-verifying every item every fleet produced.** Each member already runs its own VERIFY against the family standard. Duplicating that at the conductor tier doubles cost for no new evidence; the conductor verifies the _lane_, at batch granularity, from artifacts.
- **Fleet-ifying the convergence pipelines.** `maintenance-pipeline`, `docs-pipeline`, `design-pipeline`, `knowledge-pipeline`, and the craft pipeline are the **convergence primitive the fleets run**, not queues to fan out over. The conductor schedules fleets; a fleet composes a pipeline. Conducting pipelines directly would collapse a tier distinction the family is built on.
- **Metering tokens directly.** The harness cannot observe token spend inside dispatched subagents, so a literal token governor would be a promise the skill cannot keep. Spend is bounded by the levers that _are_ observable — concurrent agent slots, pass count, fleet count, wall-clock — and the skill says so rather than implying metering it does not have.
- **A persistent scheduler, resumable run state, or a cron surface.** A run is a session. Resumability is the `Workflow` primitive's future job, already named as the family's deterministic-execution upgrade.
- **Extracting a shared `-fleet` runtime library.** The contract stays documented in `docs/reference/fleet-family.md`; the conductor composes the members as they ship.
- **Adding members, or changing any member's behavior.** If a fleet needs a change to be conductable, that is that member's item, not this one's.

## Decisions made

1. **Build on the documented family spine; the unit at this tier is a fleet run, not an item.** `fleet-command` reuses the shared five-phase skeleton (SELECT → CONFIRM → DISPATCH → VERIFY → terminal), the worktree-isolated fan-out, the one-up-front-CONFIRM / park-unforeseen interaction model, and the never-silent-merge invariant, all stated once for the family (evidence: `docs/reference/fleet-family.md:15-53`). It keeps the family's phase **names** deliberately — a conductor that invented a private vocabulary would be harder to reason about next to the members it runs — and states the one substitution plainly: **at this tier SELECT enumerates fleets and DISPATCH dispatches fleet lanes**, where a member's SELECT enumerates items and its DISPATCH dispatches item subagents. It is **not** a `-fleet` and is not named one: members fan out over an item-queue into outcomes; the conductor coordinates the fleets themselves. It is **Tier 3** of Skills → Pipelines → Fleets → Conductor.

2. **The global governor caps concurrent per-item subagents across all fleets — not fleets, and not additively — and is imposed through each member's `--concurrency` flag.** The scarce resource is the machine-storm budget, and it is consumed by the _leaf_ agents a fleet's DISPATCH fans out, not by a fleet's own cheap SELECT / CONFIRM / VERIFY / report phases. So the governor allocates **leaf slots** from one global pool: **default 3, hard max 4**, with no single fleet ever allocated more than **2** of that pool. The sub-cap is the family's per-fleet **default**, not its ceiling of ~3: at the ceiling one lane could hold the entire default pool, which is a single-fleet run wearing a conductor's name, whereas at 2 there are always at least two lanes genuinely in flight. Fleets are admitted to DISPATCH only when a slot is free; a fleet in a cheap phase holds no slot, which is what lets several lanes be genuinely in flight while the aggregate load stays at single-fleet scale.

   **The enforcement seam is named, because a cap with no seam is the failure this member exists to fix.** All eleven members expose `--concurrency`, and the conductor imposes each lane's allocation by dispatching it with `--concurrency <allocated>`. A lane dispatched without it runs at the member's own default of 2 — chosen against a single-fleet world with no knowledge of the other lanes — which reconstitutes the additive cap one tier up. Dispatching without an explicit `--concurrency` is therefore a gate violation. Rationale: 11 members × 3 is 33 concurrent agents — the aggregate, not any member, is the storm. Capping _fleets_ instead would be the wrong unit (one fleet at its cap outweighs three fleets in SELECT); summing per-fleet governors is the failure mode this member exists to prevent. The global default sits at 3 rather than 2 because a conductor pays real scheduling latency at 2 and the family's own stated ceiling is ~3; the hard max of 4 exists so the number cannot drift upward "to go faster."

3. **The budget's enforceable units are slots, passes, fleets, and wall-clock — stated honestly, because tokens are not observable.** A run carries: the global slot cap (Decision 2); **one pass per fleet per run** (a fleet is never re-run inside a run to clear more of its queue); a **max fleets per run** (default 6 of the 11); and a **wall-clock budget** (default 8h), observed by stamping a run start timestamp and comparing elapsed time against the deadline **at each wave boundary, before the next wave is scheduled** — the only point where the check is both cheap and actionable, since no lane is mid-fan-out there. There is no mid-wave timer and none is claimed. Exhausting any budget **stops scheduling new lanes and reports partial results** — in-flight lanes are allowed to finish or park cleanly, never killed mid-write.

   **The fleet-cap shed is structural, not a ranking.** The CI trust gate and the terminal lander are **never** shed — dropping the trust gate discards the run's only read on evidence quality, and dropping the lander leaves every emission unlanded. The independent quality sweeps are shed **first, lowest probed queue depth first**. A conveyor-spine member is shed only if the human trims it at CONFIRM. Everything shed is named with which rule shed it, and the reasons are distinguishable: over the cap, empty queue, missing or errored probe, or human trim. Rationale: an unstated shed policy is a policy invented at the moment it is most convenient, and the obvious-looking "lowest queue depth first" applied globally would shed the prerequisite and the lander — the two lanes the schedule cannot do without. The wider rationale for the unit choice: the issue asks for a "concurrency/token governor," and the truthful version of that is a governor over what the harness can actually count. Claiming token enforcement it cannot perform would be exactly the kind of unverifiable promise the family's verification discipline exists to reject.

4. **The run is a hybrid DAG with a CI trust gate, a sequential spine, parallel sweeps, and a terminal lander.** Scheduling is derived, not hand-picked, and the shape is:

   | Wave                | Fleets                                                                                     | Why this wave                                                                                                                                                                                                                                                    |
   | ------------------- | ------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
   | 0 — CI trust gate   | `cicd-fleet`                                                                               | Every downstream fleet's VERIFY treats **all-OS CI green** as its evidence, so the run reads how trustworthy that signal is before anything rests on it. A **trust gate**, not a repair — see below.                                                             |
   | 1 — ideate          | `ideate-fleet`                                                                             | Ideation feeds intake, so it gets its own wave. A wave is the dependency barrier; a dependency edge _inside_ one would make "wave" mean two different things and would make "at most one batched gate round per wave" unsatisfiable whenever both are installed. |
   | 2 — intake + sweeps | `issue-fleet`; `test-fleet`, `cleanup-fleet`, `bug-fleet`, `security-fleet`, `craft-fleet` | Intake consumes ideation. The quality sweeps read standing code, so **none of their inputs** comes from the spine and they are genuinely parallel — subject to the global governor, to deconfliction (Decision 5), and to the output-coupling caveat below.      |
   | 3 — decide          | `adr-fleet`                                                                                | Consumes `issue-fleet`'s routed decisions.                                                                                                                                                                                                                       |
   | 4 — build           | `roadmap-fleet`                                                                            | Consumes the ranked queue plus the decisions above it.                                                                                                                                                                                                           |
   | 5 — terminal        | `pr-fleet`                                                                                 | Lands what every other lane produced, so it must run last or it lands a stale subset.                                                                                                                                                                            |

   A fleet whose queue is empty is **not scheduled** (an empty lane is reported, not run). A fleet the human excludes at CONFIRM drops out and its dependents are re-derived. Wave indices come from the fixed dependency shape, so an emptied wave is **skipped rather than renumbered** and is never a barrier.

   **Wave 0 is a trust gate, and the run cannot repair its own evidence base.** `cicd-fleet`'s terminal act is REPORT: it hands back **unmerged** remediation PRs and merges nothing, the conductor merges nothing, and `pr-fleet` is terminal at the last wave. So within one run, waves 1..N execute against **the same CI signal wave 0 observed**. Framing wave 0 as a precondition that _restores_ the signal would claim something the schedule cannot deliver. What the wave-0 lane actually produces within the run is **evidence-quality information plus remediation PRs whose payoff lands on the next run**. Because a red or flaky CI queue depth _is_ the signal's trust level, the read is available from SELECT's ordinary probe, and an untrustworthy signal is surfaced at CONFIRM as a **fork with a recommended default**: run `cicd-fleet` alone this session and conduct the rest next run (recommended), proceed with the full run and label every downstream verdict as resting on degraded evidence, or trim the fleets whose verdicts lean hardest on CI. Whatever the human chooses is recorded in the report.

   **The sweeps are input-independent of the spine and output-coupled to it.** `bug-fleet`, `security-fleet`, and `craft-fleet` file issues and roadmap items into exactly the queue `issue-fleet` triages, so whatever they file in wave 2 is **intake for the next run**, not this one. That is stated in the run's assumptions-made note rather than left implicit. The conductor deliberately does **not** serialize the sweeps behind intake: doing so would spend the schedule's single largest source of parallelism to freshen a queue the next run picks up anyway, for filings the human has not yet seen. Leaving "depends on none of the spine" unqualified would be false of their outputs and would hide the same stale-consumption failure the derived order exists to prevent.

   Rationale: the issue names the spine-sequential / sweeps-parallel hybrid. The two scheduling facts the issue did not state are the `cicd-fleet` **trust gate** — derived from the family's own verification standard rather than assumed, and honest about what one run can and cannot restore — and the **output-coupling** edge between the sweeps and intake.

5. **Deconfliction is a first-class product, planned from a contention map over four collision classes.** Before dispatch the conductor builds a **contention map** — which scheduled fleets are known to write which shared surfaces — and resolves it with the cheapest sufficient mechanism per class:

   | Collision class              | Example surface                                                                    | Mechanism                                                                                                                                                                                                  |
   | ---------------------------- | ---------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
   | **Generated artifacts**      | the skills catalog, the four platform command manifests, the roadmap aggregate     | **Merge-order plan + regeneration sequencing**, emitted with the report and handed to `pr-fleet` — the conductor never merges, so it plans the order rather than executing it                              |
   | **Allocated sequences**      | ADR numbers, roadmap shard slugs                                                   | **Serialize the writers into different waves** (the DAG already separates `adr-fleet` from `roadmap-fleet`); where two same-wave sweeps would allocate from one sequence, one is deferred to the next wave |
   | **Same-region source edits** | two sweeps elevating/cleaning the same module                                      | **Serialize the lanes**, not the merges: two fleets rewriting one region produce a semantic conflict no merge order fixes                                                                                  |
   | **Duplicate filings**        | one defect filed by `bug-fleet`, `security-fleet`, `test-fleet`, and `craft-fleet` | **Cross-fleet dedup at report time**: filings are collated across lanes, near-duplicates grouped into one row citing every lane that raised it, and the human sees one item, not four                      |

   **Deferral has a terminal stop.** Both serializing mechanisms push a lane into a later wave, and that push is bounded: a deferral that would place a lane **at or past `pr-fleet`'s terminal wave sheds that lane with its reason instead**. Nothing is scheduled after the lander, because a lane running after it emits work the lander cannot see — the stale-subset failure that put the lander last. Without the stop, a serialization would quietly become an unbounded push and the lane would arrive too late either to be landed or to be honestly reported as unrun.

   **The map degrades to empty, and that is a success.** If the generated-artifact conflict class is eliminated upstream — by stripping derived counters from generated prose and moving regeneration to a post-merge job on `main`, an approach already proposed in the backlog — then that row of the map simply comes back empty and the merge-order plan is a no-op. The conductor is written so its deconfliction **shrinks to nothing without breaking**, because a coordination mechanism that only makes sense against today's conflict shape would need rewriting the moment the underlying tax is fixed. Rationale: this is the single highest-value coordination job today _and_ the one most likely to shrink; designing it as a map over classes rather than as one hard-coded playbook is what lets both be true.

6. **Human gates are batched by wave, never answered — and never fired outside their wave.** The human sees: **one run-plan authorization** up front (the DAG, the fleet selection, the global budget, the contention map and its merge-order plan, the detected forks), then **one batched gate round per wave** in which every ready fleet's own CONFIRM is presented together. A fleet's CONFIRM is presented **verbatim and unmodified** — the conductor is a scheduler for these gates, not a proxy: it never pre-answers, never defaults, and never summarizes a member's gate into a yes/no. If a fleet blocks on its gate, its **lane** parks; the other lanes continue.

   The same rule constrains **probing**, and the family's two probe flags are not interchangeable. `--report-only` is the **gate-free** path (probe, present, stop, no human gate); `--dry-run` is the **gated** path (SELECT _and_ CONFIRM). SELECT may use only the gate-free path — probing through a gated one would fire a member's own CONFIRM during the conductor's Phase 1, before the run plan is even authorized, falsifying the promise that CONFIRM is the only guaranteed human touchpoint before the first lane starts. `ideate-fleet` deliberately ships no `--report-only` (a member that files nothing has no destructive mode to suppress), so it is **not probed at all**: it is recorded as **queue depth unknown**, presented that way at CONFIRM, and scheduled on the human's call. The conductor's own flags keep the same split — its `--report-only` is **non-interactive** and presents no CONFIRM, while its `--dry-run` runs SELECT and CONFIRM.

   Rationale: eleven gates arriving at unpredictable moments is worse than driving the fleets by hand, which would sink the whole proposition; but a conductor that answered them would have converted eleven human taste-checks into one machine judgment, which is precisely the collapse the authority model rejects. Batching is the only move that improves the ergonomics without touching the authority — and a probe that raises a gate has already broken it before the run begins.

7. **Iron Law — GLOBAL BUDGET, DERIVED ORDER, UNTOUCHED GATES, NEVER MERGE.** No lane is dispatched outside the global governor; no fleet runs before the fleets it depends on have finished; no member's human gate is answered, skipped, or summarized by the conductor; and nothing is merged. A violation of any of the four is a gate violation, not a tuning decision. Rationale: these four are exactly the properties that make a multi-fleet run safe to authorize at all, and each has an obvious-feeling shortcut ("just this once, run them all", "the spine is probably fine out of order", "that gate's answer is clearly yes", "it's all green, land it") — which is why they are stated as law rather than guidance.

8. **VERIFY confirms the lane from emitted artifacts, at batch granularity, and never re-runs a fleet.** A fleet reporting "ran, verified 4 items, 3 PRs open" is a claim, and the family's invariant is that a self-report is never verification (evidence: `docs/reference/fleet-family.md:44`). But re-verifying every item duplicates work the member already did to the same standard. So the conductor checks **the lane's own evidence**, per fleet:
   - **The terminal artifact exists** in the form that member's contract specifies — the emitted PRs, filed items, drafted ADRs, or ranked shortlist actually exist and are reachable.
   - **The member's VERIFY actually ran** — the lane's report carries a per-item verdict for every dispatched item, with the reference (PR/branch/item) each verdict was drawn from, and the conductor **independently spot-checks** those references rather than reading the verdicts. A lane reporting outcomes with no per-item verdicts did not run the family standard and is rejected.
   - **The invariants held — graded by the evidence actually available.** **Nothing was merged** by any lane other than a `pr-fleet` land the human authorized inside `pr-fleet`'s own gate: a **verified check**, since a merge leaves a durable trace the conductor reads directly off every branch and PR the lanes touched. **Staying within allocation** is **not** a verified check and is not reported as one — no artifact records a lane's peak concurrency, so it is a **dispatch-time-enforced property** (the lane was launched with `--concurrency <allocated>`, which _is_ checkable) **recorded as an assumption** in the run's assumptions-made note. Asserting a check with no evidence behind it would be the self-report failure this phase exists to reject, committed by the actor least entitled to commit it.
   - **CI is not applicable at this tier and is recorded as such.** The conductor emits no code and opens no PR of its own; per the family's own rule, an inapplicable check is **recorded as not-applicable**, never dropped silently, and the per-lane CI evidence stays where it belongs — inside each member's VERIFY, spot-checked here.

   A lane failing any of these is **rejected** (retried at most once for a transient failure) and reported; the run continues. Rationale: this is the one place a conductor could plausibly cheat by trusting its children, and the one place duplicating their work would double the cost of the entire run. Verifying the _lane_ from artifacts is the seam that satisfies the invariant without paying for it twice.

9. **Terminal act: REPORT — one consolidated dashboard plus the merge-order plan, and never a merge.** One run summary carrying: a per-lane row (fleet, wave, verdict, what it emitted, budget consumed, parked forks), the **cross-fleet-deduped filing list**, the **recommended merge order with its regeneration notes**, the run's budget accounting, everything the budget shed (unscheduled fleets, unstarted waves) **named with its reason rather than silently dropped**, and an **assumptions-made note** for the run. Landing is `pr-fleet`'s act under its own human gate, or the human's directly. Rationale: the report is the conductor's entire product — the value of running eleven fleets is destroyed if their outputs arrive as eleven separate reports the human must collate by hand, which is the coordination work this member exists to absorb.

10. **A quiet run is a valid, valuable result.** A run whose fleets all report empty queues is reported as **quiet** — the backlog is clear — not as a wasted run, and never as a reason to lower a noise floor or widen a queue so a lane produces something. Rationale: a conductor measured by throughput would pressure its members into manufacturing work, and it is the one actor in the family positioned to do that at scale.

## Technical design

### Skill shape

A claude-code rigid skill at `agents/skills/claude-code/fleet-command/` (`SKILL.md` plus `skill.yaml`), orchestrator-tier (`tier: 2` loading, `cognitive_mode: systematic-orchestrator`), with a domain-specific `## Rationalizations to Reject`. Platform variants (codex, cursor, gemini-cli, antigravity) are generated. The shipped body carries **no internal roadmap/PR/issue numbers** — the family spine and ADRs are cited by title only, so the skill reads correctly in an adopter project that has never heard of this repo's tracker.

### The loop — five phases (conductor-tier detail only; the skeleton is the family spine)

1. **SELECT — enumerate fleets, probe queues, derive the DAG, build the contention map.** Determine which members are installed; probe each one's queue depth via its own **gate-free** `--report-only` path only (never by reimplementing its SELECT, and never via a gated `--dry-run` path that would fire that member's CONFIRM here); record a member with no gate-free path as **queue depth unknown** and carry it to CONFIRM; drop empty-queue fleets as unscheduled; apply the fleet cap structurally (Decision 3); derive the wave assignment from the fixed dependency shape (Decision 4); build the contention map (Decision 5) and the derived merge-order plan; detect known run-level forks. Missing members degrade the DAG to those present and are recorded.
2. **CONFIRM — one run-plan authorization.** Present the DAG with its waves, the fleet selection with queue depths, the global budget (slots / passes / fleet cap / wall-clock), the contention map with its serialization and merge-order consequences, and the detected forks with recommended defaults. The human approves, trims fleets, or re-tunes the budget once. Trimming re-derives the DAG. `--dry-run` stops here.
3. **DISPATCH — schedule lanes wave by wave under the global governor.** One worktree-isolated lane per scheduled fleet, each running the **real** member skill for its stage — never a reimplementation of what that fleet does. Lanes are admitted to their fan-out phase only as global slots free up; serialized pairs from the contention map never share a wave. Each wave's ready fleets present their own CONFIRM gates together in one batched round (Decision 6). A lane that hits a genuinely unforeseen run-level fork **parks that lane and reports it**; other lanes continue. Budget exhaustion stops new scheduling and lets in-flight lanes finish or park.
4. **VERIFY — confirm each lane from its emitted artifacts (Decision 8).** Terminal artifact present; per-item verdicts present with references, spot-checked independently; nothing merged outside `pr-fleet`'s authorized land, checked directly; within-allocation reported as a dispatch-time-enforced property recorded as an assumption rather than as a verified check. All-OS CI recorded **not-applicable at this tier** with the per-lane evidence spot-checked where the members produced it. Verdicts: `verified`, `parked`, `rejected` (retried once), `unscheduled`, `quiet`.
5. **REPORT — one consolidated dashboard (Decision 9).** Per-lane rows, cross-fleet-deduped filings, the recommended merge order and regeneration sequence, budget accounting, everything shed with its reason, assumptions made. Never merges.

### Key seams and data

- **`FleetLane`** record: member name, wave, dependencies, queue depth, scheduling state (`scheduled` | `running` | `parked` | `unscheduled`), slots allocated, emitted artifacts (PRs / filed items / ADRs / shortlists), per-item verdict references, lane verdict, parked forks.
- **`RunPlan`** record: the wave-ordered DAG, the fleet selection, the global budget (slot cap, pass cap, fleet cap, wall-clock), the contention map, the derived merge-order plan, and the human's authorization.
- **`ContentionMap`**: per collision class (generated artifacts / allocated sequences / same-region source edits / duplicate filings), the fleets that touch it and the resolution applied (serialize / defer / merge-order / dedup-at-report). Degrades to empty without breaking (Decision 5).
- **Reuses:** the eleven `-fleet` members as the dispatched unit; each member's own **gate-free** `--report-only` for queue probing and each member's `--concurrency` as the seam that imposes the global allocation; the subagent worktree-isolation primitive for lane isolation; `gh` for artifact spot-checks and CI reads; `manage_roadmap` for reading filing state during dedup.
- **Global governor** at 3 leaf slots (default), hard max 4, with no fleet allocated more than **2** of the pool, imposed by dispatching every lane with `--concurrency <allocated>`.

### Integration Points

- **Entry Points** — A new claude-code skill `fleet-command` (`harness skill run fleet-command`) and its MCP `run_skill` mapping, plus the generated `/harness:fleet-command` slash command across the platform manifests. No new CLI command, MCP tool, or route.
- **Registrations Required** — Skill discovery regeneration: `harness generate` regenerates the plugin command directories (`.claude-plugin/`, `.cursor-plugin/`, `.gemini-extension/`, `.antigravity-extension/`, codex), the platform skill symlinks, and `docs/reference/skills-catalog.md` with accurate counts. A roadmap shard `docs/roadmap.d/fleet-command.md` registers the capstone in the family milestone, and the `docs/roadmap.md` aggregate is regenerated from it.
- **Documentation Updates** — `docs/reference/fleet-family.md` gains a **conductor tier** section (what the tier is, why it is not named `-fleet`, and the four properties it adds), so the family page describes the whole structure rather than only the members. No other doc edits beyond the generated catalog.
- **Architectural Decisions** — The **conductor-tier authority model** (coordinator + global governor: derived DAG scheduling, one global budget, cross-fleet deconfliction, batched-but-never-answered member gates, never auto-merge) warrants a standalone ADR. It follows the family precedent of one ADR per stage-specific authority model — the land-stage merge gate and the decide-stage batch-sign-off gate each got one — and this decision is broader than either, because it introduces a **tier** and states how authority is divided between a conductor and its members. It is captured as an ADR alongside this spec, and referenced (not restated) from `docs/reference/fleet-family.md`.
- **Knowledge Impact** — Introduces the **conductor tier** as a distinct concept: an orchestrator whose queue is other orchestrators, whose governor is global rather than local, whose verification reads its children's emitted artifacts rather than re-running them, and whose coordination product — a merge-order plan and a deduped filing list — is advice to a human rather than an executed action. Also records two derived scheduling facts: that CI trustworthiness is a **trust gate** rather than a repairable precondition for any fleet whose verification standard is all-OS-CI-green — because the remediation it produces is unmerged and therefore pays off on the next run — and that the quality sweeps are input-independent of the conveyor while being output-coupled back into it.

## Success Criteria

- Given a set of installed members and their queues, the conductor produces **one consolidated report** covering every scheduled lane, with a per-lane verdict, its emitted artifacts, and its budget consumption.
- **Every dispatched lane carries an explicit `--concurrency <allocated>`** at or below the per-fleet sub-cap of **2**, allocated from a global pool of 3 (hard max 4). That flag is the enforcement seam; a lane dispatched without it is a gate violation, and the sum of per-fleet governors is never the operative limit.
- **The run order is derived, not chosen ad hoc**: the `cicd-fleet` trust gate precedes every fleet whose verification depends on a trustworthy CI signal; the conveyor spine runs in dependency order (ideate → intake → decide → build) with **no dependency edge inside any wave**; `pr-fleet` runs last; the independent quality sweeps run in parallel alongside intake, subject to the governor and to deconfliction.
- **Wave 0 is reported as a trust gate, never as a repair**: an untrustworthy CI signal is surfaced at CONFIRM as a fork with a recommended default, `cicd-fleet`'s remediation PRs are reported as unmerged and as paying off on the next run, and any downstream verdict taken under a red signal is labelled degraded.
- **A member's own gate is never fired during SELECT**: probing uses gate-free paths only, and a member with no gate-free path is reported as queue-depth-unknown and scheduled on the human's call.
- **The fleet cap sheds structurally**: the CI trust gate and the terminal lander are never shed, the independent sweeps are shed first at lowest queue depth first, and a spine member drops only on a human trim — with every shed lane named with the rule that shed it.
- **A fleet with an empty queue is reported as unscheduled, not run**, and a fleet the human excludes drops out with its dependents re-derived.
- **Every member's own human CONFIRM gate is presented verbatim and answered only by the human.** The conductor never pre-answers, defaults, skips, or summarizes a member's gate into a yes/no. A fleet blocked on its gate parks its lane; other lanes continue.
- **The human sees one run-plan authorization plus at most one batched gate round per wave** — never eleven scattered per-fleet interruptions.
- **The contention map covers all four collision classes** and resolves each with its stated mechanism: generated artifacts get a merge-order plan with regeneration sequencing; allocated-sequence writers are serialized into different waves; same-region source-edit lanes are serialized rather than merge-ordered; duplicate filings are deduped **across fleets** at report time into one row citing every lane that raised it.
- **Deconfliction degrades to a no-op without breaking** when a collision class is eliminated upstream — an empty contention map produces an empty merge-order plan, not an error or a stale playbook. A serialization deferral that would reach `pr-fleet`'s terminal wave sheds its lane with a reason rather than scheduling past the lander.
- **The run is bounded**: one pass per fleet, a fleet cap (default 6), and a wall-clock budget (default 8h) compared against a run start timestamp at each wave boundary before the next wave is scheduled. Exhausting any budget **stops scheduling and reports partial results with everything shed named and reasoned** — in-flight lanes finish or park cleanly and are never killed mid-write.
- **No lane verdict rests on a fleet's self-report.** Every `verified` lane is backed by an independently-confirmed terminal artifact, per-item verdicts carrying references that the conductor spot-checked itself, and a directly-checked nothing-merged record. Within-allocation is reported as a dispatch-time-enforced property recorded as an assumption, not as a verified check, since no artifact records a lane's peak concurrency.
- **The merge-order plan contains only lanes that emit mergeable artifacts** — a lane that files nothing, emits no PR, or is `pr-fleet` itself never appears in it.
- **The sweeps' output-coupling to intake is stated, not hidden**: their filings are recorded in the assumptions-made note as intake for the _next_ run, with the reason they are not serialized behind intake.
- **All-OS CI is recorded as not-applicable at the conductor tier**, explicitly and with its reason — never silently omitted — because the conductor emits no code and opens no PR of its own; per-lane CI evidence stays inside each member's VERIFY and is spot-checked.
- The conductor **never merges**, and never authorizes a land on the human's behalf; its merge-order plan is advice attached to the report.
- The conductor **never schedules a convergence pipeline directly** — pipelines are the primitive its fleets run.
- A run whose fleets all report empty queues is reported as **quiet** — a valid outcome, never a reason to widen a queue or lower a noise floor so a lane produces something.
- It **degrades gracefully**: a missing member, a parked lane, or a single rejected lane is reported while the run continues; a rejected lane is retried at most once.
- **Every report carries an "assumptions made" note** (the derived DAG and why, the budget in force and the `--concurrency` each lane was dispatched with, the contention resolutions applied, the sweeps' filings recorded as next-run intake, and the defaults taken).
- `harness skill validate fleet-command` passes; the shipped body carries **no internal roadmap/PR/issue numbers**.
